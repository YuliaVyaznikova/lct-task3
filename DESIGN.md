## 0. Что строим

Веб-прототип «помощник диспетчера» (ТЗ §0–§2). Вход — заявки и инженеры одного региона на один день. Выход — распределение заявок по инженерам, порядок посещения, времена прибытия/начала/окончания, маршруты на карте и таймлайне, две обязательные метрики (число задействованных инженеров; пробег по каждому и суммарно), сравнение с базовым вариантом из ТЗ §2.3, объяснение каждого назначения и причины каждого неназначения языком диспетчера, перепланирование после события (срочная заявка / отмена / инженер недоступен) с наглядным diff.

Оптимизатор — Google OR-Tools (VRPTW с пропуском узлов и фиксированной стоимостью машины). Бэкенд — Python/FastAPI. Фронтенд — React + TypeScript + Leaflet. Хранение — JSON-файлы. Запуск — одна команда.

Принцип из ТЗ (§8, последняя страница): побеждает завершённый и понятный прототип, а не сложная архитектура. Всё, что помечено **MVP**, делается обязательно и первым; **should** — после того как MVP работает end-to-end; **won't** — не делается.

### 1.2 Колонки

Синтетика: `Заявка; Тип заявки BK; Тип заявки HD; Начало; Окончание; Район; Адрес; [Подключение;] Гигабитное подключение`.
Контроль: то же плюс `Статус BK` (после «Тип заявки BK») и `Бригада` (после «Адрес»).

Колонка `Подключение` (значения `FMC`/`FTTB`/пусто) есть **только у Востока**. Буква «BK» в заголовке — латиница. После таблицы синтетики — две пустые строки и строка `Адрес Офиса;<адрес>;;;…` (в Югоцентре — `Адрес офиса`, с маленькой «о»). Адаптер должен искать строку офиса регистронезависимо по префиксу «Адрес оф».

Синтетика = контроль минус `Статус BK`, минус `Бригада`, минус номер квартиры в адресе, с новыми пятизначными ID. Порядок строк совпадает построчно; по нему можно сопоставить синтетическую заявку с контрольной (нужно только для опционального «факт vs план»). В контроле Юго-Востока один дублирующийся ID (305898293 — отменена и выполнена, одна и та же заявка) — для нас несущественно.

### 1.3 Значения

`Тип заявки BK` (4 значения, одинаковы во всех регионах): `Подключение`, `Дозаказ`, `Локальная заявка`, `Глобальная проблема`.

`Тип заявки HD` под ними: Подключение → Конвергенция абонента / Заявка на подключение / Заказ подключения/Дозаказ оборудования; Дозаказ → Дозаказ оборудования / Заказ подключения/Дозаказ оборудования / (1 раз) Конвергенция абонента; Локальная заявка → Нет линка, Низкая скорость, Разрывы, Рост ошибок на порту, IP-адрес 169..., Работа с кабелем, Переключение на Гбит/с, Роутер. Замена техническим специалистом, TVE/ENT. Замена приставки техником, TVE/ENT. Другие ошибки, ТВ. Замена приставки техником, Мониторинг; Глобальная проблема → **Авария** или **Информация**.

Окна — двухчасовые слоты `10–12, 12–14, 14–16, 16–18, 18–20, 20–22` (последний слот заканчивается в 22:00 — смены инженеров должны это покрывать), плюс у аварий Юго-Востока `0:01–23:59` (11 штук). Остальные аварии (Восток — 3, часть Юго-Востока) стоят в обычных двухчасовых слотах. «Глобальная проблема / Информация» — окна двухчасовые, это не авария.

Адреса: `Город Москва, ул.Артюхиной, д. 20А`, `г.Город Москва, б-р.Самаркандский, д. 32к1` (аварии — с префиксом «г.», без пробела в корпусе), `Домодедово, ул.Корнеева, д. 50`, `Кашира, ул.Садовая, д. 18`, `МО, г. Кашира Кржижановского ул. д. 5/1`, `обл.Московская область, г.Домодедово, пгт.Востряково-1, ул.Жуковского, д. 14/18`, `Москва Бирюлевская ул. д. 44`. Форматов несколько — геокодер должен получать нормализованную строку (§4.4).

География: Восток и Югоцентр — компактные московские районы. **Юго-Восток содержит три подмосковных кластера — Домодедово (12 заявок), Кашира (16), Ступино (4)** — на 25–100 км от офиса на Бирюлёвской. В контроле их обслуживают выделенные бригады (Паршин — Домодедово; Саламатин, Козырь — Кашира/Ступино). Пешеход/ОТ до Каширы за смену не доедет; это надо учесть в генераторе инженеров (§4.3) и это же — естественный источник неназначенных заявок с честной причиной.

Статусы в контроле (нам — только для событий): Не отправлена, Отправлена, В пути, В работе, Выполнена, Отменена, Просрочена. Отменённых: Восток 6, Юго-Восток 10, Югоцентр 5.

## 4. Данные

### 4.1 Адаптер выгрузки Билайна — `planner/ingest/beeline.py`

`load_region(synthetic_csv, control_csv | None) -> Scenario` (без инженеров и координат — их добавляют следующие шаги).

1. Прочитать через `csv.reader(encoding="cp1251", delimiter=";")`. Заголовок — первая строка; индексы колонок брать по имени (наборы колонок различаются между регионами).
2. Таблица заявок — строки, у которых первая ячейка — число. Строка офиса — первая ячейка начинается с `адрес оф` (регистронезависимо); адрес — вторая ячейка. Если офис не найден — ошибка.
3. `window_start/end` — время из `Начало`/`Окончание` (`dd.mm.yyyy H:MM`, час может быть без ведущего нуля: `0:01`). Дата сценария — из первой строки.
4. `skill`, `duration_min`, `priority` — по таблице §4.2.
5. `id` — `<код региона>-<номер строки, 3 цифры>`; порядок строк файла сохраняется — это «порядок поступления» для baseline (ТЗ §2.3).
6. `attributes.connection` — из колонки `Подключение` если есть; `attributes.gigabit` — `Да` → true.
7. Если передан контроль: сопоставить построчно (i-я строка синтетики ↔ i-я строка контроля; проверить совпадение `Тип заявки BK`, окна и района, иначе — предупреждение и пропуск), записать `attributes.control_status`, `attributes.control_engineer`. Строки со `control_status == "Отменена"` → в `scenario.events` заготовка `cancel_order` со временем = начало окна − 50 мин.
8. Коды регионов: Восток `V`, Юго-Восток `YV`, Югоцентр `YC`; `id` сценария: `vostok`, `yugo-vostok`, `yugocentr`.

### 4.2 Маппинг типов и нормативы

Источник длительностей — `Нормативы.xlsx` (официально, чат 16.09).

| `Тип заявки BK` | `Тип заявки HD` | `skill` | `duration_min` | `priority` |
|---|---|---|---|---|
| Подключение | любой | connection | 70 (60 + 10) | normal |
| Дозаказ | любой | connection | 20 (10 + 10) | normal |
| Локальная заявка | любой | local | 30 (30 + 0) | normal |
| Глобальная проблема | Авария | emergency | 80 (80 + 0) | **urgent** |

### 4.4 Геокодирование — `planner/ingest/geocode.py`

Офлайн-скрипт `python -m planner.cli geocode --region all`. Кэш `data/cache/geocode.json` (ключ — нормализованный адрес). Результат записывается в сценарий; **в рантайме сервис к геокодеру не обращается**.

Нормализация перед запросом (`normalize_address`): убрать префиксы `г.Город Москва`, `Город Москва`, `Москва`, `МО,`, `обл.Московская область,` → регион «Москва» либо «Московская область» по наличию `Домодедово|Кашира|Ступино|Востряково`; `пр-кт.` → `проспект `, `ул.` → `улица `, `б-р.` → `бульвар `, `проезд.`/`пр-зд.` → `проезд `, `пер.` → `переулок `, `наб.` → `набережная `, `ш.` → `шоссе `; `д. 128 к 5` → `128к5`; `д. к5` (Самаркандский Квартал 137а) — особый случай: `Самаркандский бульвар, квартал 137А, к5`; `Кржижановского ул. д. 5/1` → `улица Кржижановского, 5/1`.

Ни один адрес не правится руками. Для каждого адреса выполняется лестница попыток; первая удачная фиксирует `geocode_quality` и провайдера. Ключи — необязательные переменные окружения: если ключа нет, ступень пропускается, пайплайн работает на OSM-сервисах.

| Ступень | Провайдер | Условие | Запрос | `geocode_quality` |
|---|---|---|---|---|
| 0 | `data/config/geocode_overrides.csv` | файл есть (по умолчанию пуст) | — | `manual` |
| 1 | **DaData Suggest** (`suggestions.dadata.ru/suggestions/api/4_1/rs/suggest/address`, заголовок `Authorization: Token $DADATA_KEY`, 10 000 запросов/сутки бесплатно, ключ — регистрация по email) | `DADATA_KEY` задан | `{"query": <исходный адрес как есть>, "count": 1}`; из ответа `data.geo_lat/geo_lon`, `data.qc_geo` | `qc_geo` 0–1 → `exact`; 2 → `street`; 3–5 → отбросить |
| 2 | **Яндекс Геокодер** (`geocode-maps.yandex.ru/1.x/?apikey=$YANDEX_GEOCODER_KEY&geocode=…&format=json`, 1 000 запросов/сутки бесплатно) | `YANDEX_GEOCODER_KEY` задан | нормализованная строка; из ответа `metaDataProperty.GeocoderMetaData.precision` | `exact`/`number` → `exact`; `street` → `street`; иначе отбросить |
| 3 | **Nominatim** (`nominatim.openstreetmap.org`, обязательный `User-Agent`, 1 запрос/с) | всегда | structured: `street=<улица>, <дом с корпусом>`, `city=<Москва \| Домодедово \| Кашира \| Ступино>`, `country=Россия` | `exact` |
| 4 | Nominatim | всегда | то же без корпуса/строения (`д. 128 к 5` → `128`) | `exact` |
| 5 | **Photon** (`photon.komoot.io/api/?q=…&lang=ru`, без ключа) | всегда | нормализованная строка целиком | `exact`, если в ответе есть `housenumber`, иначе `street` |
| 6 | Nominatim | всегда | только улица + город → центроид улицы | `street` |
| 7 | центроид района из `data/config/districts.csv` (заполняется тем же скриптом по названию района + город) + детерминированный джиттер 300 м (seed = hash адреса) | всегда | — | `district` |

Ключи читаются из `.env` в корне (`DADATA_KEY=…`, `YANDEX_GEOCODER_KEY=…`) либо из файлов `dadata-key.txt` / `yandex-key.txt` в корне; `.env`, `*-key.txt` — в `.gitignore` с первого коммита, в отчёты и логи ключи не попадают.

DaData стоит первой, потому что у неё координаты для 97 % домов Москвы, явный код точности и терпимость к разнобою форматов в нашем датасете (`МО, г. Кашира Кржижановского ул. д. 5/1`, `г.Город Москва, б-р.Самаркандский, д. 32к1`). Один адрес = один запрос, всего ~205. Google Geocoding не используется: бесплатный лимит есть, но требует биллинг-аккаунт с банковской картой.

Проверка каждого ответа: точка в 120 км от офиса региона (для московских адресов — в 25 км) и, если известен район, в 5 км от его центроида; иначе результат отбрасывается и берётся следующая ступень. Между ступенями провайдер и ответ пишутся в кэш, повторный запуск ничего не дёргает. Отчёт `data/cache/geocode_report.md` — по каждому адресу ступень, провайдер, координаты; ожидание с DaData — ≥ 95 % `exact`, без ключей — ≥ 85 %. Погрешность 300 м у оставшихся не меняет ни распределение, ни демонстрацию; в UI такие точки помечаются пунктирной обводкой.

Показ карты — Leaflet + OSM-тайлы, без ключей (Яндекс JS API бесплатен до 500 запросов/сутки, но лишняя зависимость; Google Maps JS требует биллинг).

## 5. Модель движения — `planner/core/travel.py`

`class TravelModel: matrix(points: list[(lat, lon)], transport) -> (dist_m: int[N][N], time_min: int[N][N])`. Считается один раз на сценарий и тип транспорта; кэш `data/cache/matrices/<hash>.npz` (hash от точек + модели).

**`HaversineTravel`** — по умолчанию, офлайн, детерминирована. `dist = haversine × 1.3`. Время:

| Транспорт | Время | Легенда |
|---|---|---|
| car | dist / 22 км/ч + 5 мин | средняя городская с пробками и парковкой |
| bike | dist / 14 км/ч + 2 мин | |
| foot | dist / 4.5 км/ч | |
| public | dist < 1.2 км → как foot; иначе 12 мин + dist / 18 км/ч | подход + ожидание + наземный транспорт |

Калибровка (тест): средний переезд между соседними заявками одного московского района — 10–25 мин, что согласуется с нормативом «Дорога 20 мин».

**`OsrmTravel`** (should) — профили `car`/`bike`/`foot` через `/table?annotations=duration,distance` публичного `router.project-osrm.org` или локального контейнера; `public` — как в Haversine. Результат кэшируется в репозитории; при любой ошибке — fallback на Haversine с записью в `plan.params.travel_model`.

## 6. Планировщик — `planner/core/solver.py`

### 6.1 Формализация

Переменные: назначение заявки инженеру или пропуск; порядок; время начала `s_o`.

Жёсткие ограничения (ТЗ §2.2):
1. Квалификация: `skill(o) ∈ skills(e)`.
2. Время: `s_o ∈ [win_start, win_end]`; `s_o ≥ arrival_o = finish_prev + travel_e(prev, o)`; `finish_o = s_o + duration_o`; `finish_last ≤ shift_end(e)`; выезд из старта не раньше `shift_start(e)`.
3. Ресурс: `required_transport(o) ∈ {null, transport(e)}`.

Целевая функция (единицы — метры):
```
min  Σ_o drop(o)·[o пропущена] + F·|{e : маршрут непуст}| + Σ_e dist_e
   + Σ_{o: urgent} w_u · max(0, s_o − shift_start_e) + S · Σ_o [e(o) ≠ e_prev(o)]
```
Константы по умолчанию: `drop(normal)=1 000 000`, `drop(connection)=1 500 000`, `drop(urgent)=10 000 000`; `F=100 000` в режиме `min_engineers`, `F=0` в режиме `min_distance`; `w_u=50` м/мин; `S=500` м (только при перепланировании, иначе 0). Порядок величин гарантирует лексикографику: суммарный пробег региона < 100 км = 100 000 м < F < drop.

### 6.2 Отображение на OR-Tools

- Узлы: `0..E-1` — стартовые узлы инженеров (все в офисе, но по одному на инженера, чтобы при replan стартовать из разных точек); `E..E+N-1` — заявки; `E+N` — фиктивный конечный узел. `RoutingIndexManager(E+N+1, E, starts=[0..E-1], ends=[E+N]*E)`.
- Дуги в конечный узел: расстояние 0, время = только `duration(i)` — тогда cumul в конце маршрута = окончание последней работы.
- Время — `AddDimensionWithVehicleTransits(transit_cb_per_vehicle, slack_max=1440, capacity=1440, fix_start_cumul_to_zero=False, "Time")`, где `transit_v(i,j) = duration(i) + time_transport(v)(i,j)`; slack = ожидание начала окна. Cumul в узле = **время начала работ**.
- Окна: `Time.CumulVar(node).SetRange(win_start, win_end)`. Смена: `Time.CumulVar(Start(v)).SetRange(shift_start, shift_start)` (при replan — время доступности), `Time.CumulVar(End(v)).SetMax(shift_end)`.
- Стоимость дуг — `SetArcCostEvaluatorOfVehicle(cb_v, v)`, `cb_v(i,j) = dist_transport(v)(i,j) + S·[prev_engineer(j) ≠ v]`.
- Пропуск: `AddDisjunction([node], drop(o))`.
- Квалификация/транспорт: `routing.SetAllowedVehiclesForIndex(allowed(o), node)`. Если `allowed(o)` пуст — узел в модель не добавляется, причина ставится предфильтром (§10.2).
- Минимум инженеров: `SetFixedCostOfAllVehicles(F)`.
- Срочность: `Time.SetCumulVarSoftUpperBound(node, shift_start_min_over_allowed, w_u)`.
- Обед (should): `Time.SetBreakIntervalsOfVehicle([IntervalVar 13:00–14:00 длительностью 45, гибкий], v, node_durations)`.
- Поиск: `PATH_CHEAPEST_ARC` + `GUIDED_LOCAL_SEARCH`, `time_limit` из params (по умолчанию 10 с; демо — 5 с). При replan — начальное решение `ReadAssignmentFromRoutes(prev_routes_filtered, True)`.
- Результат → список маршрутов (порядок `order_id` по инженерам) → **валидатор** (§8) пересчитывает все времена и метрики. Солвер никогда не пишет времена в `Plan` напрямую.

Размер: ≤ 100 заявок × 12 инженеров — секунды. Если `time_limit` истёк без решения (не должно случаться при disjunctions) — вернуть план baseline с пометкой.

## 9. Перепланирование — `planner/core/replan.py`

`replan(scenario, plan, event, params) -> (Plan, Diff)`; `t` = время события в минутах.

1. Заморозка по текущему плану, для каждого инженера: стопы с `finish ≤ t` — выполнены, остаются `locked: true`; стоп с `start < t < finish` — в работе, считается доводимым до конца: инженер стартует из его точки в момент `finish`; стопы с `start ≥ t` — в пул. Инженер без начатых стопов после `t` стартует из точки последнего выполненного (или офиса) в момент `max(t, shift_start)`. Если у инженера стоп с `arrival < t < start` (ждёт на адресе) — считаем, что начнёт по плану: стоп фиксируется, старт с его точки в `finish`.
2. Событие: `urgent_order` — заявка добавляется с `priority: urgent`, окно как задано (если `window_end < t` — 422); `cancel_order` — заявка удаляется; если уже выполнена — 409 с текстом; `engineer_unavailable` — инженер исключается с `t`, его начатая и последующие заявки — в пул.
3. Решение §6 на пуле + новые старты, `S = stability_weight_m`, warm-start из предыдущих маршрутов (без снятых узлов). Ранее неназначенные участвуют снова.
4. `Diff` (§3) и `summary`: «Срочная заявка YV-099 назначена Инженеру 07: ближайший свободный с навыком «Аварийные работы» (2.1 км, прибытие 12:52). YV-020 перенесена с Инженера 07 на Инженера 02 (начало 13:10 → 13:40). Пробег +3.4 км, инженеров по-прежнему 8, неназначенных 3 → 3».

## 10. Объяснения — `planner/core/explain.py`

### 10.1 Назначенная заявка

```jsonc
{
  "headline": "Инженер 03 · прибытие 09:47, начало 10:00, окончание 11:10",
  "checks": [
    { "ok": true, "text": "Навык «Подключение и дозаказы» — есть (навыки инженера: локальные, подключение)" },

  ],
  "travel": "От предыдущей точки (YV-005, ул. Артюхиной, 20А): 1.4 км, 17 мин",
  "alternatives": [
    { "engineer_id": "E07", "feasible": true,  "delta_km": 3.1, "text": "Инженер 07 — +3.1 км к его маршруту" },

```

Альтернативы — контрфактически: для каждого другого инженера с подходящим навыком/транспортом ищется дешевейшая допустимая вставка заявки в его **итоговый** маршрут (через валидатор, O(len)); возвращаются `delta_km` или конкретное сломанное ограничение.

### 10.2 Неназначенная заявка — `diagnose(order, scenario, plan)`

Иерархия, первая сработавшая причина:
1. Нет координат → `NO_COORDS`.
2. Нет инженера с навыком → `NO_SKILL`: «Нет ни одного инженера с навыком «Аварийные работы»».
3. Есть навык, но не совпадает требуемый транспорт → `NO_TRANSPORT`: «Требуется автомобиль; инженеры с навыком «Подключение» — пешеходы и ОТ».
4. Ни у одного подходящего инженера смена не покрывает окно → `SHIFT_MISMATCH`: «Окно 20:00–22:00, смены подходящих инженеров заканчиваются в 18:00».
5. Дорога от старта до заявки у каждого подходящего дольше, чем `win_end − shift_start` → `UNREACHABLE`: «До адреса (Кашира) 95 км — пешком и на ОТ не добраться в окно; автомобилисты с навыком … заняты/отсутствуют».
6. Иначе `CAPACITY`: «Все 4 инженера с навыком «Подключение» заняты в окно 10:00–12:00: Инженер 03 освобождается в 12:20, Инженер 07 — в 11:50 в 40 мин езды…» — формулировка из ближайшей неудачной вставки (какое ограничение сломалось и на сколько минут).

Тот же модуль используется baseline'ом.

### 10.3 План и маршрут

`plan_explanation`: «Задействовано 8 из 12 инженеров. Назначено 58 из 61. Не назначено 3: 2 — нехватка мощности в окно 10:00–12:00, 1 — нет навыка. Чтобы выполнить всё, нужен ещё +1 инженер с навыком «Подключение»». `extra_engineers_needed` — жадная укладка неназначенных на виртуальных инженеров (все навыки, `car`, смена 09:00–22:00) с дешевейшей вставкой; число задействованных виртуальных = ответ. Постановщик на Q&A назвал такую формулировку желательной.

`route_explanations[e]`: «Инженер 03: 6 заявок, 9.8 км, 96 мин в пути, 60 мин ожидания, смена загружена на 78 %. Порядок задают окна: 10–14 — Текстильщики (3 заявки рядом), 14–18 — Кузьминки».

## 14. Интерфейс

Один экран, десктоп-first, три зоны.

**Слева (280 px) — управление:** выбор сценария; параметры (режим «меньше инженеров / меньше пробега», лимит времени, обед); кнопка «Спланировать»; блок «Событие»: вкладки «Срочная заявка» (адрес кликом по карте или из списка, навык, окно, длительность по умолчанию из нормативов), «Отменить заявку» (выбор из плана), «Инженер недоступен» (инженер + время); кнопка «Перестроить план».

**Центр — карта (Leaflet):** офис (иконка), заявки (круг, цвет = инженер, номер = порядок; красная обводка — неназначена; молния — срочная; серые — выполненные до `t` при replan), маршруты-полилинии по инженерам (прямые отрезки; при OSRM — геометрия `/route`); клик по заявке — карточка §10.1/§10.2; после события — режим diff: изменённые заявки подсвечены, переключатель «до / после», список изменений.

**Справа (420 px) — таймлайн и таблицы:** Gantt по инженерам 09:00–22:00 (блоки заявок, цвет по навыку; серые отрезки — дорога; штриховка — ожидание; вертикальная линия `t` при replan); под ним вкладки: «Маршруты» (кто, куда, во сколько), «Неназначенные» (заявка, причина), «Метрики» (карточки + таблица «наш план / базовый / Δ» с зелёными и красными дельтами), «Изменения» (после события).

Цвета инженеров фиксированы по индексу. Все тексты — русские, термины диспетчера. Никаких «vehicle», «node», «disjunction» в UI.

## 17. Демо-сценарий (ТЗ §4, 5–7 минут)

1. Открыть «Демо» (Восток, 12 инженеров, 66 заявок) — показать заявки, инженеров со навыками и транспортом.
2. «Спланировать» — карта, таймлайн, метрики.
3. Клик по заявке — объяснение назначения с альтернативами.
4. Неназначенная — причина и «+N инженеров».
5. Событие «срочная авария 12:30» → «Перестроить» → diff: кто поехал, что сдвинулось, метрики до/после.
6. Событие «отмена» → освободившееся время подбирает ранее неназначенную (если получилось на демо-seed).
7. Вкладка «Метрики»: наш план vs базовый — инженеры, пробег, назначено.
8. Переключить регион «Юго-Восток» — тот же цикл на данных с Подмосковьем: неназначенные в Кашире с причиной `UNREACHABLE`/`CAPACITY`.

## 19. Допущения (в `docs/ASSUMPTIONS.md` и README)

1. Один день, один регион за прогон; старт всех инженеров — офис региона; возврат не требуется.
2. Бригада = один инженер.
3. Навыки, транспорт, смены инженеров и `required_transport` у части заявок — синтетические по справочникам ТЗ §2.4.1, детерминированный генератор с seed.
4. Длительности — из официальных нормативов (тех. работы + документы); время в пути — модель §5 (коэффициент извилистости 1.3, средние скорости, ОТ как «подход + ожидание + наземный»).
5. Пробки, парковка, подъём в квартиру — усреднены в скоростях.
6. Приоритет: «Авария» — срочная; «Информация» — обычная выездная заявка навыка «Аварийные работы»; подключения — повышенный вес при пропуске.
7. Контрольное распределение в расчётах не используется; служит для числа инженеров и опциональной витрины «факт vs план».
8. Оборудование, FMC/FTTB, гигабит — информационные атрибуты, не ограничения. Обед — опция.
9. Событие вводит диспетчер вручную; статусы в реальном времени не поступают. При недоступности инженера начатая заявка возвращается в пул.
10. Пробег для всех типов транспорта — длина пути по модели движения, км.
11. Подмосковные заявки Юго-Востока остаются в регионе; недостижимые честно показываются как неназначенные с причиной.
