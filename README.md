# Интеллектуальный сервис планирования рабочих маршрутов для инженеров

Решение задачи №3 от «билайн бизнес» на хакатоне «Лидеры цифровой трансформации 2026».
Команда «Ежи».

Прототип помощника диспетчера: распределяет заявки между старшими инженерами
домашнего интернета, строит маршрут каждому, показывает план на карте и
таймлайне, объясняет каждое назначение понятным языком и перестраивает план
после события в течение дня.

---

## Запуск

```bash
git clone <репозиторий> && cd <репозиторий>
docker compose up --build
# открыть http://localhost:8000
```

Без Docker:

```bash
python -m venv .venv
.venv/Scripts/pip install -e .            # Linux/macOS: .venv/bin/pip
cd frontend && npm install && npm run build && cd ..
.venv/Scripts/python -m planner.cli serve  # http://127.0.0.1:8000
```

Данные (сценарии с координатами и инженерами) уже лежат в `data/scenarios/`
и подготовлены к запуску — сеть и ключи для работы сервиса не нужны.
Пересобрать их с нуля можно так:

```bash
python -m planner.cli build       # CSV выгрузки  -> сценарии
python -m planner.cli geocode     # адреса        -> координаты (нужна сеть)
python -m planner.cli engineers   # справочник инженеров
python -m planner.cli demo        # демонстрационный набор с событиями
```

Расчёт без интерфейса, с таблицей сравнения:

```bash
python -m planner.cli plan --region demo --time-limit 20 --verbose
```

Тесты: `python -m pytest -q` (около 250 проверок, три минуты).

Визуальная проверка интерфейса — прогон сценария защиты в headless-браузере
со снимками каждого шага (нужен запущенный сервис и установленный Chrome):

```bash
python tools/demo_flow.py screenshots
```

## Что умеет решение

Обязательный минимум по ТЗ §2.1 и §2.5 закрыт полностью:

| Требование ТЗ | Где |
|---|---|
| Загружать тестовые данные из CSV/JSON либо встроенный набор | `ingest/beeline.py`, `POST /api/scenarios/upload` |
| Распределять заявки между инженерами | `core/solver.py` |
| Определять порядок посещения адресов | `core/solver.py` |
| Показывать маршруты и точки на карте | `frontend/src/components/MapView.tsx` |
| Краткая информация «кто, куда, во сколько» | вкладка «Маршруты», таймлайн |
| Перестраивать план после события | `core/replan.py`, все три вида событий |
| Объяснять результат языком диспетчера | `core/explain.py`, `core/reasons.py` |
| Явно показывать неназначенные заявки с причиной | вкладка «Не назначены» |
| Обязательные метрики и сравнение с базовым вариантом | `core/metrics.py`, вкладка «Метрики» |

Сверх минимума: ручное переназначение с проверкой ограничений, выбор критерия
оптимизации, необязательный обеденный перерыв, оценка «нужно ещё +N инженеров»,
метрика риска опоздания, выгрузка результата в формате ТЗ §2.4.2.

## Схема решения

```
интерфейс (React + Leaflet)
        │  HTTP
        ▼
    API (FastAPI)  ──  api/app.py, api/store.py
        │
        ▼
      ядро
   ├─ solver.py     оптимизатор (OR-Tools, VRPTW)
   ├─ baseline.py   базовый вариант из ТЗ §2.3
   ├─ validate.py   арифметика маршрута и проверка ограничений
   ├─ metrics.py    метрики и сравнение
   ├─ replan.py     перепланирование по событию
   ├─ explain.py    объяснения
   ├─ reasons.py    причины отказа
   └─ travel.py     время в пути и расстояния
        │
        ▼
     данные
   ├─ ingest/beeline.py    выгрузка билайна  -> канонический формат
   ├─ ingest/address.py    разбор адресов
   ├─ ingest/geocode.py    координаты
   ├─ ingest/engineers.py  синтетический справочник инженеров
   └─ data/scenarios/*.json
```

Ключевое архитектурное решение: **валидатор — единственный источник истины**.
Времена, пробег и метрики никогда не берутся из солвера напрямую, а всегда
пересчитываются в `validate.py`. Через него проходят и оптимизатор, и базовый
вариант, и ручное переназначение. Благодаря этому показанное пользователю
не может разойтись с тем, что на самом деле посчитал оптимизатор, а план
с нарушением ограничений не может попасть в интерфейс физически.

## Логика оптимизации

Задача — VRPTW с гетерогенным парком, пропуском узлов и платой за выход
инженера на смену. Целевая функция (единицы — метры):

```
min  Σ drop(o)·[заявка пропущена]
   + F·|задействованные инженеры|
   + Σ пробег
   + Σ w·(насколько поздно начата срочная заявка)
   + Σ S·[заявка сменила инженера]        (только при перепланировании)
```

| Константа | Значение | Смысл |
|---|---|---|
| `drop` обычной | 1 000 000 | пропуск заявки дороже любого маршрута |
| `drop` подключения | 1 500 000 | подключения приоритетнее прочих (Q&A) |
| `drop` срочной | 10 000 000 | аварию не пропускаем никогда |
| `F` | 100 000 | плата за вывод инженера на смену |
| `w` | 50 м/мин | «аварию выполнить как можно раньше» |
| `S` | 3 000 | штраф за перевод заявки к другому инженеру |

Порядок величин делает критерии лексикографическими: никакая экономия
километров не оправдывает лишнего инженера, и никакая экономия инженеров
не оправдывает пропуска заявки. Это ровно тот порядок, который назвал
постановщик на сессии вопросов и ответов: больше выполненных заявок →
меньше исполнителей → короче маршруты.

Режим **«выбрать лучшее автоматически»** решает задачу дважды — с платой за
инженера и без неё — и берёт лучший результат по этой же лексикографике.
Нужен потому, что когда сократить штат нельзя, плата за инженера становится
константой, но сбивает направленный поиск: на Востоке разница доходила
до 21 % пробега.

Математический оптимум не доказывается, ТЗ §2.3 этого и не требует.

### Обязательные ограничения (ТЗ §2.2)

1. **Квалификация** — требуемый навык заявки входит в навыки инженера.
2. **Время** — начало работ попадает во временное окно; работа с учётом дороги
   и длительности укладывается в смену. Приехать раньше окна можно (это
   ожидание), начать работу раньше — нет. Окончание за пределами окна допустимо,
   за пределами смены — нет.
3. **Ресурс** — если у заявки задан требуемый тип транспорта, он совпадает
   с транспортом инженера.

Учёт оборудования ТЗ относит к необязательному усложнению; поля выгрузки
(FMC/FTTB, гигабитное подключение) переносятся в заявку как справочная
информация и ограничений не создают.

## Метрики

Две обязательные по ТЗ §2.3:

* **задействовано инженеров** — сколько уникальных исполнителей получили
  хотя бы одну заявку;
* **пробег** — по каждому исполнителю отдельно и суммарно по плану.

Дополнительно считаем **пробег на выполненную заявку**. Без него сравнение
с базовым вариантом вводит в заблуждение: план, который везёт на 28 заявок
больше, неизбежно накатывает больше километров, хотя работает эффективнее.

### Базовый вариант

Задан в ТЗ §2.3 дословно: заявки в порядке поступления, каждая — первому
по порядку во входных данных подходящему инженеру, порядок посещения равен
порядку назначения, глобальной оптимизации нет. Реализован в `baseline.py`
и считается при каждом построении плана.

Результат на выданных данных:

| Участок | Назначено | Инженеров | Пробег на заявку |
|---|---|---|---|
| Демонстрационный | **60** против 31 | **11** против 12 | **2,7** против 6,7 км |
| Восток | **59** против 34 | **11** против 12 | **3,2** против 6,3 км |
| Юго-Восток | **63** против 35 | 12 против 12 | **7,2** против 17,3 км |
| Югоцентр | **55** против 27 | 11 против 11 | **3,1** против 6,1 км |

### Справочно: сопоставление с фактом

Контрольный файл выгрузки содержит то, как заявки были распределены между
бригадами в реальности. Эталоном он не является и в оптимизации не участвует
(указание постановщика от 17.09), но эксперты закономерно спрашивают, как
решение соотносится с действительностью, а использовать обезличенные данные
«для демонстрации» постановщик разрешил. Расчёт доступен командой
`python -m planner.cli control` и на вкладке «Метрики».

| Участок | Заявок закрыто | Пробег на заявку | Исполнителей | Визитов начато позже окна |
|---|---|---|---|---|
| Восток | 59 против 64 | **3,2** против 3,8 км | **11** против 12 | **0** против 1 |
| Юго-Восток | 63 против 83 | 7,2 против **6,9** км | 12 против 12 | **0** против 17 |
| Югоцентр | 55 против 56 | **3,1** против 4,0 км | 11 против 11 | **0** против 3 |

Фактическое распределение не укладывается в собственные нормативы компании:
часть визитов начиналась позже окна, обещанного клиенту. Постановщик это
подтверждал на сессии вопросов и ответов — «де-факто по всем нормативам
был overbooking». Наш план таких нарушений не допускает по построению.

**Про Юго-Восток говорим прямо: по километрам на заявку мы там проигрываем.**
Сравнение не равное — факт закрывает все 83 заявки, но 17 визитов начинает
позже окна; мы берём 63 и не нарушаем ни одного. Наборы обслуженных заявок
разные, поэтому удельный километраж считается по разным множествам. Довести
участок до полного покрытия без нарушений двумя местными бригадами нельзя —
решение прямо говорит, сколько исполнителей для этого не хватает.

и описать допущения, что и сделано: число инженеров равно числу бригад

по рабочим минутам, транспорт и смены — по квотам из конфигурации.

|---|---|---|
| Алгоритм и бэкенд | Python 3.11+, FastAPI, Google OR-Tools | по рекомендации ТЗ §3.2 |
| Интерфейс | React + TypeScript + Vite | ТЗ допускает React либо Streamlit\* |
| Карта | OpenStreetMap + Leaflet | по рекомендации |
| Хранение | JSON-файлы | ТЗ §3.2 относит СУБД к необязательному |
| Запуск | Docker, публичный стенд не требуется | по рекомендации |

\* Streamlit не подошёл: обязательное по ТЗ наглядное отображение того,
что именно изменилось после события, требует интерактивного сравнения
«до / после» на карте и таймлайне, а не перерисовки страницы целиком.

Геокодирование выполнено офлайн заранее, координаты хранятся в репозитории.
Использована лестница бесключевых и бесплатных сервисов: DaData (ключ выдаётся
по регистрации, 10 000 запросов в сутки), затем Nominatim и Photon, в крайнем
случае — центроид района. Из 205 адресов 96 % определены точно до дома.
В рантайме сервис к геокодерам не обращается.

## Расхождения с планом

Замысел решения зафиксирован в [DESIGN.md](DESIGN.md) до написания кода.
Реализация отошла от него в шести местах — все перечислены в §21 того же
документа: модель движения, отказ от кэша матриц, OSRM с отличием от замысла,
выездные базы инженеров, калибровка расстояний по дорожной сети
и сопоставление с фактическим распределением. Невыполненных пунктов плана
не осталось. Исходные формулировки плана оставлены нетронутыми.

## Известные ограничения прототипа

* Горизонт — один рабочий день и один участок за прогон; переносы на другие
  дни не моделируются (по условию задачи).
* Время в пути считается по модели со средними скоростями, а не по
  маршрутизатору: пробки, парковка и подъём к квартире усреднены.
  Коэффициент перевода прямой в дорогу откалиброван по реальной сети
  (`python -m planner.cli calibrate`): медианная ошибка 8,8 %.
  Маршрутизатор OSRM подключается по желанию переменной `OSRM_URL`
  и даёт настоящие расстояния по дорогам; время при этом остаётся нашим —
  публичный сервер считает без пробок и план вышел бы невыполнимым.
* Учёт оборудования, составы бригад из нескольких человек и повторные визиты
  вынесены за рамки, как и предусмотрено ТЗ.
* Статусы выполнения в реальном времени не поступают: событие вводит диспетчер
  вручную. Механика перепланирования к приёму потока статусов готова — нужен
  только источник.

## Идеи дальнейшего развития

* Подключить маршрутизатор с учётом общественного транспорта и исторических
  пробок по часам — модель движения для этого уже вынесена за интерфейс.
* Планирование на несколько дней вперёд и работа со слотами, которые открываются
  за месяц: в реальном процессе распределение идёт на следующий день, а слоты
  ставятся заранее.
* Подсказка диспетчеру по составу оборудования, которое инженеру нужно взять
  с собой утром, — все данные для этого в заявках уже есть.
* Приём статусов «в пути / в работе / выполнено» и автоматическое
  перепланирование по факту отклонения от плана.
