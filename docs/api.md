# HTTP API

Вернуться к [README.md](../README.md). Устройство сервиса описано в [architecture.md](architecture.md).

Базовый адрес: `http://127.0.0.1:8000`. Сообщения об ошибках для диспетчеров выводятся на русском языке. Интерактивная схема FastAPI доступна по адресу `/docs`.

## Сценарии

`GET /api/health` возвращает состояние сервиса и число загруженных сценариев.

`GET /api/scenarios` возвращает список регионов с их идентификаторами, названиями, датами, числом заявок и инженеров, минимальным числом инженеров, числом подготовленных событий и адресами офисов.

`GET /api/scenarios/{scenario_id}` возвращает полный сценарий: заявки, координаты, временные окна, инженеров, офис и события.

`GET /api/reference` возвращает `skills`, `transports`, `reason_codes`, `work_types` и `travel_model`. Виды работ в `work_types` содержат нормативную длительность.

`POST /api/scenarios/upload` принимает сценарий в формате CSV или JSON. Адреса из CSV геокодируются, а состав инженеров создаётся заново по настройкам региона. При ошибке геокодирования возвращается сообщение с дальнейшими действиями. Загрузка не заменяет сохранённый сценарий: если его идентификатор уже занят, новый сценарий сохраняется как `<id>-2`, `<id>-3` и так далее, а номер добавляется к названию.

## Планирование

`POST /api/plans` строит план. Тело запроса:

```json
{
  "scenario_id": "demo",
  "engineer_count": 11,
  "params": {
    "objective": "auto",
    "time_limit_s": 30,
    "no_improve_s": 6,
    "seed": 42,
    "lunch": false,
    "allow_reschedule": false,
    "travel_model": "haversine"
  }
}
```

Параметр `objective` принимает `auto`, `min_engineers`, `min_distance` или `balanced`. В API значение `auto` считает `min_engineers` и `min_distance` в параллельных процессах, а затем `balanced`, который начинается с готового плана `min_distance`. Основной план выбирается из первых двух вариантов сначала по числу назначенных заявок, затем по числу задействованных инженеров и пробегу. Значение `balanced` добавляет к пробегу штраф за загрузку самого занятого инженера и никогда не закрывает меньше заявок, чем план, с которого начал. `time_limit_s` ограничивает каждый поиск; `no_improve_s` по умолчанию равен 6 секундам и останавливает поиск, если улучшений нет. Необязательный `engineer_count` заново формирует состав инженеров, сохраняя заявки. `allow_reschedule` разрешает выход за окна клиентов только при перепланировании.

Ответ имеет форму `PlanResponse` с полями `optimized`, `baseline`, `comparison`, `control`, `scenario` и `variants`. Поле `variants` содержит до трёх записей `{key, title, plan_id, metrics}` с ключами `min_engineers`, `min_distance` и `balanced`. Каждый вариант сохраняется как отдельный план. При `lunch=true` каждый `Route` содержит `break: {start, finish} | null`; время остановок учитывает перерыв. Остановка также содержит время `departure`.

`POST /api/plans/jobs` принимает такой же запрос и сразу возвращает `{job_id}`. `GET /api/plans/jobs/{job_id}/events` передаёт поток событий Server-Sent Events:

- `progress`: `{elapsed_s, variant, assigned, total, engineers_used, distance_km, routes}`; поле `routes` сопоставляет идентификаторам инженеров упорядоченные массивы идентификаторов заявок. Обновления поступают не чаще четырёх раз в секунду.
- `done`: полный `PlanResponse`, включая `variants`.
- `error`: `{detail}`, если фоновый расчёт завершился ошибкой.

`GET /api/plans/{plan_id}` возвращает сохранённый план в форме `PlanResponse`. `POST /api/plans/{plan_id}/select` делает этот вариант рабочим планом и возвращает его `PlanResponse`.

## События в течение дня

`POST /api/plans/{plan_id}/events` перестраивает план после одного события. Тело запроса имеет один из следующих видов:

```json
{ "type": "urgent_order", "time": "12:30", "order": { "...": "полная заявка" } }
{ "type": "new_order", "time": "12:30", "order": { "...": "полная заявка" } }
{ "type": "cancel_order", "time": "11:10", "order_id": "V-009" }
{ "type": "engineer_unavailable", "time": "13:00", "engineer_id": "E03" }
{ "type": "engineer_delayed", "time": "13:00", "engineer_id": "E03", "minutes": 30 }
```

`urgent_order` всегда помечает заявку как срочную независимо от приоритета в теле запроса; этот тип сохранён для совместимости. `new_order` сохраняет исходный приоритет заявки, поэтому обычную заявку, поступившую в течение дня, передают через него. Для обычной заявки перепланирование повышает стоимость передачи уже назначенных заявок другим инженерам, но не запрещает такую передачу.

Остановки, к которым инженер выехал до события или в момент события, остаются зафиксированными. Инженер становится доступен не раньше момента события и окончания последней зафиксированной остановки. Задержка дополнительно запрещает новые выезды до `time + minutes`. При перепланировании бюджет поиска по умолчанию составляет 8 секунд. Ответ имеет форму `ReplanResponse` с полями `plan`, `diff` и `scenario`; `diff` описывает изменённые заявки, маршруты, зафиксированные остановки и метрики.

`POST /api/plans/{plan_id}/events/jobs` принимает такое же событие и возвращает `{job_id}`. Ход расчёта передаётся через `GET /api/plans/jobs/{job_id}/events`; событие `done` содержит полный `ReplanResponse`.

## Работа с планом

`POST /api/plans/{plan_id}/manual` назначает заявку инженеру или снимает её с маршрута, если `engineer_id` равен `null`. Необязательный `position` задаёт индекс вставки с нуля или значение `"best"` по умолчанию. Проверяются те же ограничения маршрута, что и при автоматическом планировании.

`GET /api/plans/{plan_id}/candidates/{order_id}` возвращает по одной строке для каждого инженера: `{engineer_id, feasible, reason_code, reason, position, arrival, start, added_km, donor_removed_km, total_delta_km, shifted, preview_routes}`. Поле `shifted` содержит `{order_id, from_start, to_start}` для остановок, у которых меняется время начала в любом из затронутых маршрутов. Сначала идут допустимые варианты, отсортированные по `total_delta_km`. Передайте возвращённый `position` в ручной метод, чтобы применить показанную вставку.

`GET /api/plans/{plan_id}/explain/{order_id}` возвращает карточку с объяснением заявки. Для назначенных заявок она содержит проверки ограничений и альтернативы; для неназначенных возвращаются код причины и текст.

`GET /api/plans/{plan_id}/geometry` сохраняет поле `routes` с дорожной линией маршрута каждого инженера и добавляет `legs` с отдельной линией до каждой остановки от начальной точки инженера вдоль маршрута. Если дорожная геометрия недоступна, участок отображается прямым отрезком. Геометрия нужна для отображения и не влияет на планирование.

`GET /api/plans/{plan_id}/export` выгружает упорядоченные визиты и время по каждому инженеру, инженера или причину отказа по каждой заявке, а также общие метрики по инженерам и пробегу.
