# HTTP API

Назад в [README.md](../README.md). Рядом: [architecture.md](architecture.md) про то, где этот слой стоит в решении.

Базовый адрес `http://127.0.0.1:8000`. Все тексты ошибок на русском, потому что их показывает диспетчеру интерфейс. Интерактивная схема доступна на `/docs`, её отдаёт FastAPI.

## Сценарии

`GET /api/health` отвечает состоянием сервиса и числом загруженных сценариев.

`GET /api/scenarios` возвращает список участков: идентификатор, название, дату, число заявок, число инженеров, минимально допустимое число инженеров, число заготовленных событий и адрес офиса.

`GET /api/scenarios/{scenario_id}` отдаёт сценарий целиком: заявки с координатами и окнами, инженеров, офис, события.

`GET /api/reference` возвращает справочники: навыки, типы транспорта, приоритеты, виды оборудования и типы работ с нормативной длительностью.

`POST /api/scenarios/upload` принимает свой набор данных в CSV или JSON. Адреса геокодируются при загрузке, справочник инженеров достраивается, если его нет. Если координаты определить не удалось, возвращается понятная ошибка с подсказкой, чем собрать сценарий заранее.

## Планирование

`POST /api/plans` строит план. Тело запроса:

```json
{
  "scenario_id": "demo",
  "engineer_count": 11,
  "params": {
    "objective": "auto",
    "time_limit_s": 30,
    "seed": 42,
    "lunch": false,
    "allow_reschedule": false,
    "travel_model": "haversine"
  }
}
```

Поле `objective` принимает `auto`, `min_engineers` или `min_distance`. Поле `engineer_count` необязательное: если его передать, состав бригад пересобирается генератором под нужное число, а заявки остаются теми же. Поле `allow_reschedule` разрешает сдвигать обещанное клиенту время, оно работает только при перепланировании.

В ответе приходит оптимизированный план, базовый вариант, таблица сравнения, сопоставление с фактическим распределением и сам сценарий. У плана есть идентификатор, по нему работают остальные ручки.

`GET /api/plans/{plan_id}` возвращает ранее построенный план в том же виде.

## Событие в течение дня

`POST /api/plans/{plan_id}/events` перестраивает план. Тело это само событие, одно из четырёх видов:

```json
{ "type": "urgent_order", "time": "12:30", "order": { "...": "полный набор полей заявки" } }
{ "type": "new_order",    "time": "12:30", "order": { "...": "полный набор полей заявки" } }
{ "type": "cancel_order", "time": "11:10", "order_id": "V-009" }
{ "type": "engineer_unavailable", "time": "13:00", "engineer_id": "E03" }
```

Разница между `urgent_order` и `new_order` в приоритете. Первый всегда помечает заявку срочной, каким бы ни был приоритет в теле, он оставлен для совместимости. Второй берёт приоритет из самой заявки, поэтому именно через него подаётся обычная заявка, поступившая в течение дня. Обычная заявка встраивается в свободное время и не переводит уже назначенные заявки к другим инженерам.

В ответе новый план, сценарий и разбор изменений: какие заявки добавились и пропали, какие сменили исполнителя, у каких сдвинулось время, сколько визитов заморожено как уже начатые, какие маршруты затронуты и как изменились метрики.

## Работа с планом

`POST /api/plans/{plan_id}/manual` переназначает заявку вручную. В теле идентификатор заявки и идентификатор инженера, либо `null`, чтобы снять заявку с исполнителя. Ограничения проверяются так же, как при автоматическом расчёте, поэтому недопустимое переназначение не пройдёт.

`GET /api/plans/{plan_id}/explain/{order_id}` возвращает карточку объяснения. Для назначенной заявки это проверки по каждому ограничению и разбор альтернатив, во что обошлась бы заявка другим инженерам. Для неназначенной код причины и её формулировка.

`GET /api/plans/{plan_id}/geometry` отдаёт ломаные маршрутов по дорогам. Нужны только для отрисовки на карте, на расчёт не влияют.

`GET /api/plans/{plan_id}/export` выгружает результат в формате, который требует задание: по каждому исполнителю упорядоченный список заявок с плановым временем и пробегом, по каждой заявке назначенный исполнитель либо причина отказа, по плану в целом число задействованных исполнителей и пробег.
