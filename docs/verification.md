# Проверка и показ

Назад в [README.md](../README.md). Здесь описано, как проверить решение без чтения кода: прогнать тесты, получить таблицу результатов из [algorithm.md](algorithm.md#результаты), независимо проверить план и пройти демонстрацию из пункта 4 задания.

## Тесты

```bash
uv run python -m pytest -q
# без uv: .venv/Scripts/python -m pytest -q
```

Тесты проверяют ограничения на маленьких примерах и на настоящих участках, базовый вариант, перепланирование по каждому событию, объяснения и причины отказа, HTTP API и требования задания по пунктам. Полный прогон занимает около двенадцати минут, потому что часть тестов считает планы оптимизатором.

Осмотреть собранные сценарии можно командой `uv run python -m planner.cli show --region all`.

## Таблица результатов

Числа в [algorithm.md](algorithm.md#результаты) получены через HTTP API тем же запросом, которым план считает интерфейс. Чтобы их воспроизвести, запустите сервис и посчитайте каждый участок:

```bash
docker compose up --build -d
for region in demo vostok yugo-vostok yugocentr; do
  curl -fsS -H 'Content-Type: application/json' \
    -d "{\"scenario_id\":\"$region\",\"params\":{\"objective\":\"auto\"}}" \
    http://localhost:8000/api/plans > "$region.json"
done
```

В ответе нужные поля лежат так: покрытие, число задействованных инженеров и пробег в `optimized.metrics`, те же показатели базового варианта в `baseline.metrics`, пробег по каждому инженеру в `distance_by_engineer`, неназначенные заявки с причинами в `optimized.unassigned`, сверка с фактом в `control`. Все числа одной строки таблицы берите из одного ответа.

Поиск ограничен временем по часам, поэтому на другой машине результат может отличаться на несколько процентов. Наш замер сделан на процессоре Intel Core i5-1240P, три прогона каждого участка дали одинаковый результат. Время ответа удобно смотреть той же командой с `time` перед `curl`.

## Независимая проверка плана

Все времена и метрики сервис берёт из валидатора, поэтому повторный вызов валидатора ничего нового не докажет. Для независимой проверки достаточно небольшого скрипта, который читает сохранённый ответ и сверяет с полем `scenario` ключевые правила: у инженера есть нужный навык и транспорт, работа начинается внутри окна клиента и заканчивается до конца смены, каждая заявка встречается ровно один раз среди назначенных и неназначенных.

Причина `CAPACITY` у неназначенной заявки означает, что заявку не удалось вставить без нарушений в найденный план. Это не доказательство невозможности вообще: при другой перестановке нескольких заявок она могла бы встать. Список «Кому можно назначить» в карточке заявки показывает, к кому её можно поставить прямо сейчас и какие визиты при этом сдвинутся.

## Демонстрация

Семь шагов пункта 4 задания в интерфейсе на `http://localhost:8000`:

1. Открыть данные. В верхней панели выбран участок «Демонстрационный день», полоса показателей показывает 66 заявок, 12 инженеров и 3 события.
2. Запустить планирование кнопкой «Спланировать день». Первый допустимый план появляется меньше чем через секунду и дальше улучшается, внизу видны три варианта плана.
3. Показать распределение и маршруты на карте. Слева список инженеров, справа очередь заявок.
4. Открыть заявку в очереди. Карточка показывает, какие ограничения проверены, почему выбран этот инженер и во что заявка обошлась бы другим. У неназначенной заявки показана причина и ближайшее свободное окно, которое можно предложить клиенту.
5. Ввести событие на вкладке «Симуляция». Подготовлены отмена заявки в 11:10, авария в 12:30 и недоступность инженера в 13:00, их применяет движение часов. Там же можно добавить своё событие любого из пяти типов.
6. Показать изменения. После каждого события видно, сколько визитов сдвинуто и сколько закреплено, изменённые заявки подсвечены на карте, в очереди и в расписании, в полосе показателей видна разница с прежним планом.
7. Сравнить с базовым вариантом на вкладке «Сравнение с базовым»: покрытие, число инженеров, пробег суммарно и по каждому инженеру, сверка с фактическим распределением.

Эти же шаги автоматически проходит `tools/demo_flow.py`. Скрипт открывает интерфейс в Chrome или Edge без окна, выполняет шаги по очереди, проверяет результат каждого и сохраняет снимки экрана. Ему нужен пакет websocket-client, поэтому при работающем сервисе он запускается так: `uv run --with websocket-client python tools/demo_flow.py screenshots`. Адрес сервиса по умолчанию `http://127.0.0.1:8000`, другой задаётся переменной `PLANNER_URL`.
