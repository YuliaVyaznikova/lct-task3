# Проверка и сценарий показа для проверяющего

Эта процедура объединяет количественный аудит плана с проверкой текущего сценария работы диспетчера. Она описывает проверки, которые нужно выполнить, а не уже полученные результаты. Краткую заметку с результатами, JSON-ответы, при необходимости диагностические журналы, реестр неназначенных заявок и скриншоты или запись демонстрации сохраняйте в `runtime/runs/YYYY-MM-DD/`. Каталог `runtime/` игнорируется Git, поэтому сырые выводы остаются локальными. Фиксируйте ветку или метку релиза, состояние локальных изменений, модель CPU, версии Python/OR-Tools/Node в той среде, которая считает каждый план, seed и конфигурацию генерации инженеров, сценарий, цель, модель движения и фактический бюджет расчёта. Публикуйте числа в [algorithm.md](algorithm.md#результаты) только после того, как финальный прогон их воспроизведёт.

## Подготовка и осмотр поставляемых данных

Запускайте из корня репозитория. Предварительные требования описаны в корневом [README](../README.md). Полный существующий набор тестов обязателен; `-rs` выводит причину каждого пропуска, чтобы её можно было исследовать и записать, не перезапуская набор только ради этого.

```bash
uv sync --extra dev
uv run --extra dev pytest -q -rs
uv run python -m planner.cli show --region all
uv run python -m planner.cli show --region demo
```

Сборка Docker ниже компилирует интерфейс, поэтому отдельный локальный `npm ci && npm run build` нужен только при запуске сервиса вне Docker. Селектор `all` в `show` охватывает три предоставленных участка; `demo` осматривается отдельно. Зафиксируйте, задан ли `OSRM_URL` для процесса, который выполняет расчёт. Текущий файл Compose не передаёт его в контейнер, поэтому API-прогоны в нём используют офлайн-модель движения. Дорожная геометрия на карте не является моделью времени в пути.

## Получение итогового сравнения

Используйте Docker Compose как проверку чистого запуска и как API-источник для таблицы результатов. Запустите его в фоне, затем вызовите `POST /api/plans` трижды для каждого сценария с `objective=auto` и `time_limit_s=30`. Сохраняйте каждый ответ целиком, прежде чем сводить его в таблицу. Четыре ID сценариев: `demo`, `vostok`, `yugo-vostok` и `yugocentr`.

```bash
docker compose up --build -d
curl --retry 10 --retry-connrefused --retry-delay 2 -fsS http://localhost:8000/api/health
RUN_DIR="runtime/runs/$(date +%F)"
mkdir -p "$RUN_DIR"
docker compose exec planner python -c \
  "import sys, ortools; print(sys.version); print('ortools', ortools.__version__)" \
  > "$RUN_DIR/versions.txt"
for region in demo vostok yugo-vostok yugocentr; do
  for run in 1 2 3; do
    curl -fsS -H 'Content-Type: application/json' \
      -d "{\"scenario_id\":\"$region\",\"params\":{\"objective\":\"auto\",\"time_limit_s\":30}}" \
      http://localhost:8000/api/plans > "$RUN_DIR/$region-$run.json"
  done
done
```

В текущем API `auto` запускает три варианта параллельно (`min_engineers`, `min_distance` и `balanced`), каждый с полным ограничением `time_limit_s`; основной оптимизированный план выбирается из первых двух. Поэтому настройка в 30 секунд это ограничение поиска на один вариант плюс накладные расходы процесса и API. Для покрытия, задействованных инженеров и пробега указывайте медиану и разброс по трём полным прогонам. Отдельные прогоны оставляйте видимыми, а не выбирайте лучший. Поиск, ограниченный по реальному времени, может меняться в зависимости от скорости машины, поэтому фиксируйте CPU.

Каждый сохранённый ответ также фиксирует свои условия: `optimized.params.travel_model` это фактически использованная модель движения, а `scenario.meta.generator_seed` это seed генерации инженеров.

Все числа одной строки результатов берите из одного и того же ответа API. CLI полезен для читаемой трассировки маршрута, но пропускает часть нужных столбцов. Эти поля делают полную таблицу воспроизводимой:

| Результат | Источник в одном ответе `POST /api/plans` |
|---|---|
| Назначено из общего числа, задействованные инженеры, суммарные км, км на выполненную заявку | `optimized.metrics`; соответствующие значения базового варианта в `baseline.metrics`. |
| Пробег по инженерам для обоих планов | `optimized.metrics.distance_by_engineer` и `baseline.metrics.distance_by_engineer`. |
| Покрытие по ярусам приоритета | Сопоставьте ID заявок в `optimized.routes[].stops[]` (или `baseline.routes[].stops[]`) с `scenario.orders[].priority_tier`; знаменателем служит число всех заявок сценария в каждом ярусе. Одного `urgent_assigned` недостаточно для полной разбивки по ярусам. |
| Каждый ID неназначенной заявки, код и текст | `optimized.unassigned[]`; сопоставьте с `scenario.orders[]`, чтобы получить навык, транспорт, окно, атрибуты, связанные с оборудованием, и приоритет. |
| Контекст исторического контроля | `control` в этом же ответе; держите его покрытие и оговорки рядом со сравнением. |
| Результат встроенного валидатора | Успешный ответ с планом означает, что `solver.plan()` вызвал `evaluate()` без нарушений. Ошибка означает неудачный прогон, а не результат с нулём нарушений. |

Небольшой одноразовый скрипт извлечения может читать сохранённые JSON-файлы и строить эти таблицы или реестр неназначенных заявок. Это инструмент анализа, а не тестовая фикстура и не замена сырым ответам. `uv run python -m planner.cli plan --region demo --objective auto --time-limit 30 --verbose` может вывести маршруты и причины для диагностики, но выполняет ещё один прогон оптимизатора; не смешивайте его числа со строкой из API. Точно так же `uv run python -m planner.cli control --region all --time-limit 30` заново запускает оптимизатор, поэтому его столбец «наш план» может отличаться от прогона через API. Используйте его только как отдельно подписанный контекст.

По итоговым ответам обновите [algorithm.md](algorithm.md#результаты) и слайды. Держите рядом с каждым результатом среду, цель, модель движения, бюджет расчёта и покрытие. Разница между прогонами сама по себе не доказывает ни дефект кода, ни оптимальность.

## Аудит допустимости и неназначенных заявок

Оптимизатор уже вызывает `evaluate()` и берёт времена и метрики из этого валидатора. Повторный вызов `evaluate()` на том же плане не даёт независимого подтверждения. Чтобы независимо проверить ключевые правила кейса, небольшой одноразовый проверяющий скрипт может сравнить сохранённые JSON `scenario` и `optimized`, не вызывая функций проверки планировщика: требуемый навык и транспорт; начало работ на каждой остановке внутри окна её клиента; окончание до конца смены; каждая заявка встречается ровно один раз среди назначенных и неназначенных; назначенные плюс неназначенные равны всем заявкам сценария. Зафиксируйте, какие правила этот скрипт действительно покрывает. Арифметика времени в пути по маршруту и оборудование остаются на встроенном валидаторе и существующих целевых тестах, если их отдельно не реализовать заново.

Заведите в реестре строку для каждой неназначенной заявки с ID, ярусом приоритета, окном, требованиями к навыку, транспорту и оборудованию, возвращённым кодом и текстом и подтверждением. Группируйте причины так: навык и транспорт, окно и смена, оборудование, география и дорога, ограничение поиска. Никогда не описывайте промах ограниченного поиска как доказанную невозможность.

Для каждой заявки с `CAPACITY` сначала проверьте статическую совместимость, затем попробуйте каждую позицию вставки в маршрут каждого совместимого инженера, используя `evaluate()` на копии назначения маршрутов этого прогона. Включайте и совместимых инженеров без назначенных заявок как маршрут из одной остановки: вывести простаивающего инженера дешевле, чем потерять заявку, поэтому оптимизатор может это сделать. Стройте `Geo` из сохранённого `scenario` с той же моделью движения, что и в API-прогоне: проверьте `optimized.params.travel_model` в сохранённом JSON и запускайте скрипт без `OSRM_URL`, когда это значение офлайн-модель, иначе локальная дорожная модель сделает результат вставки бессмысленным. Вставка без нарушений свидетельствует о том, что возвращённое объяснение про нехватку ресурсов слишком сильное; запишите заявку, инженера, позицию и получившийся план, чтобы исправить объяснение. Если ни одна вставка не работает, прогоните этот сценарий ещё раз с ограничением `auto` 60–90 секунд на вариант и отметьте, размещена ли заявка. Неудача в обеих проверках всё равно не доказывает глобальную недопустимость: может понадобиться перестановка нескольких заявок. Держите эти более длинные прогоны отдельно от таблицы сравнения на 30 секунд.

Также проверьте жёсткие правила в читаемом выводе маршрута: приехать можно раньше, но работа начинается внутри окна клиента; работа заканчивается в пределах смены инженера; первый переезд начинается из стартовой точки этого инженера; обратный переезд не требуется; длительность работы на адресе и смоделированная дорога учитываются по одному разу; смоделированный командой запас оборудования не превышается. Первичное планирование не может сдвигать обещанные окна. Официальные длительности и то, как в них учитывается дорога, описаны в [case-rules.md](case-rules.md#официальные-длительности-как-не-учесть-дорогу-дважды).

## Сценарий показа для диспетчера на смоделированном дне

Используйте финальную сборку Docker и откройте `http://localhost:8000` при ширине 1440 и 1024 px. Фиксируйте в датированном прогоне ветку и коммит, размер окна браузера, действия, наблюдаемые результаты, сбои и горизонтальное переполнение. Это протокол показа, а не утверждение, что текущая сборка его прошла. Скриншоты храните локально в игнорируемом каталоге `frontend/` этого прогона.

1. Выберите `demo` и нажмите `Спланировать день`. Пока идёт расчёт, проверьте, что обновляются индикатор хода, KPI и карта. Когда расчёт закончится, осмотрите все три карточки вариантов и выберите один. Запишите покрытие, задействованных инженеров и пробег из одного и того же выбранного плана. Откройте назначенную и неназначенную заявки, посмотрите их объяснения для диспетчера и сделайте предпросмотр одного ручного переназначения через `Отдать другому`. Применяйте только допустимого кандидата; причину недопустимости записывайте отдельно.
2. Откройте `Расписание` и проверьте порядок посещения, плановое время, имена инженеров и отметку текущего времени. Откройте `Сравнение с базовым` и сравните покрытие, задействованных инженеров и пробег с базовым вариантом «первый подходящий». Не сравнивайте пробег без покрытия.
3. Перед последовательностью событий постройте новый план `demo`. Откройте `Симуляция`. Подготовленная шкала событий содержит отмену в 11:10, срочную заявку в 12:30 и недоступность инженера в 13:00. На стартовом времени добавьте обычную `Новая заявка` с типом работ и окном клиента из списка; событие применяется, когда часы доходят до его времени. Запишите, размещена ли заявка в этом прогоне, её инженера и время начала, если она назначена, а также получившиеся изменённые и замороженные визиты. Промах поиска не доказывает, что заявка невыполнима.
4. Проиграйте или перемотайте вперёд подготовленные события отмены, срочной заявки и недоступности инженера по порядку времени. На каждом перепланировании часы встают на паузу. Проверьте индикатор хода, исход события, число сдвинутых и замороженных визитов, обновлённые карту и расписание и то, остаются ли визиты, к которым инженер уже выехал, за своим инженером. Если перепланирование не удалось, запишите ошибку и с помощью `Сначала` воспроизведите её от исходного плана, прежде чем продолжать.
5. После подготовленных событий поставьте паузу и добавьте `Задержка` для инженера с оставшейся работой. Запишите длительность задержки, время события, первый новый выезд, изменённые визиты и неразмещённую работу, если она есть. Проверьте, что ни один новый выезд этого инженера не раньше окончания задержки. Та же форма событий предлагает `Авария` и `Отмена` для отдельной проверки, если подготовленное событие не может показать эти пути.
6. С помощью `Сначала` убедитесь, что план, часы и подготовленная шкала событий возвращаются в исходное состояние. Повторите показ при обеих ширинах окна и отметьте горизонтальное переполнение. Для утверждений о времени, метриках и заморозке сохраняйте сырые ответы API; одного интерфейса недостаточно для подтверждения этих правил.

Синтетические атрибуты инженеров, приблизительное время в пути и ограниченный поиск описаны в [README](../README.md) и в [допущениях](assumptions.md), а не в поясняющем тексте интерфейса. Неудачный запрос подложки карты сам по себе не является сбоем оптимизатора. Итоговую запись экрана снимайте только после решения по интерфейсу и финального прогона Docker.
